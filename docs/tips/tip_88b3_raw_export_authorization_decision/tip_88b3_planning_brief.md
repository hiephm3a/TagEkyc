## 0. Grounding (on-code recon @ 3e7ec76)

### 0.1 Security model - MODEL B (trusted application authorization boundary)
B3's authorization ENGINE is C# (the repository/application code): it opens one ambient transaction, calls the landed C# B1 eligibility resolver and the B2 consent resolver, applies the class-selection / ceiling / coverage / expiry / cause logic, and writes the decision. The DB does NOT claim permit ELIGIBILITY is DB-enforced. The DB enforces INTEGRITY only: row shape (CHECK), append-only (deny UPDATE/DELETE), parent/child same-transaction atomicity (xmin guard), the actor GUC (fail-closed), no direct table DML by runtime, and function ACLs.

Model A (one high-level DB authorization function that internally revalidates all gates) is INFEASIBLE and rejected: the landed 88B1 eligibility resolver is C# (`EfRawExportControlPlaneRepository.ResolveExportEligibilityForAuthorizationAsync`), so a DB function cannot call it without re-implementing 88B1 eligibility in SQL - out of scope and a different design. Model B is the only model consistent with the landed C# resolvers + repository-only surface.

Consequence pinned: low-level helper DB functions are NOT broadly runtime-callable. `tagekyc_runtime` may EXECUTE exactly three B3 functions: (1) the session-lock function; (2) the idempotency claim/read function; and (3) ONE atomic persistence function that writes the final decision, all evidence children, and - only when Authorized - the permit + permit classes. There is NO standalone runtime-granted permit-insert function and NO standalone authorized-decision-insert function. Everything the DB "enforces" is integrity, not the authorization verdict. The authorization verdict's correctness is a property of the C# boundary + the two landed resolvers it consumes.

## 2. Scope - ALLOWED

### 2.1 Surface + one authenticated actor
A new `IRawExportAuthorizationRepository.AuthorizeExportAsync(AuthorizeRawExportCommand command)` returning `Task<RawExportAuthorizationResult>`. The command carries ONE actor value plus the request:
- `AuthenticatedRawExportActor Actor` - a record copied ATOMICALLY from `AuthenticatedClientContext` at the API/caller boundary: `{ PrincipalId:Guid, ClientApplicationId:Guid, ApiKeyId:Guid }`. There is NO overload accepting three independent Guids. The SAME `Actor` is used for: the actor GUC (`SET LOCAL tagekyc.actor_principal_id = Actor.PrincipalId`), the 88B1 principal argument (`Actor.PrincipalId`), the session-owner comparison (`Actor.ClientApplicationId`), the idempotency key + fingerprint, and the decision evidence. Anti-mixing tests assert a decision can never bind a PrincipalId/ClientApplicationId/ApiKeyId from anywhere but the one `Actor`.
- Request: `RequestedVerificationSessionId:Guid`, `PolicyId:Guid`, `PolicyVersion:int`, `RequestedRawClasses?` (a typed nullable ordered list; NO caller-supplied selection mode), `IdempotencyKey:string` (grammar 2.7). B3 DERIVES `RawClassSelectionMode` internally (Option-B, 2.8): `RequestedRawClasses == null` => `DefaultPolicySet`; a supplied non-empty unique set => `ExplicitSubset`. The DERIVED mode is what the decision, fingerprint, and evidence bind; there is no caller-supplied mode to be inconsistent.
B3 does NOT authenticate and opens NO HTTP surface (the authenticator -> context -> app-service -> HTTP wiring + API contract + public envelopes are a LATER surface slice, 2.10). B3 DOES own typed repository input validation (2.8 preflight).
Return type (pinned): `AuthorizeExportAsync` returns `Task<RawExportAuthorizationResult>` - the immutable decision GRAPH: the decision record + its ordered eligibility causes + fulfillment refs + class snapshots + (Authorized only) the permit + permit classes. The SAME `RawExportAuthorizationResult` shape is returned for a freshly-persisted `NewClaim` and for a replayed `ExistingMatch` (loaded via 2.9). A preflight failure (2.8) throws a typed `RawExportAuthorizationInputException`; a `FingerprintConflict` and the operational/invariant rollbacks throw typed exceptions (no partial result).

### 2.2 Requested vs resolved session identity
Decision carries BOTH `RequestedVerificationSessionId` (NOT NULL, no FK, in the idempotency key/fingerprint) and `ResolvedVerificationSessionId` (nullable FK). `SESSION_NOT_FOUND` => resolved NULL + session snapshot NULL. Existing => resolved == requested + snapshot populated. `Authorized` + permit REQUIRE resolved NOT NULL; the permit binds ONLY the resolved session.

### 2.3 Authorization transaction order (pinned; one atomic transaction; B1 is the eligibility authority)
Preflight (2.8) first: syntactic request + Option-B class validation; a preflight failure returns a typed input error with NO transaction, NO idempotency claim, NO durable decision.
Then, in ONE B3-opened transaction:
1. `SET LOCAL tagekyc.actor_principal_id = Actor.PrincipalId`;
2. claim/read idempotency (2.4) and BRANCH on the typed outcome: `ExistingMatch` -> LOAD the existing immutable graph by the stored `ExportDecisionId` (2.9 ExistingMatch replay read path), commit/return, with NO session/B1/B2/policy re-evaluation and NO persist call; `FingerprintConflict` -> ROLL BACK, surface `RAW_EXPORT_AUTHORIZATION_IDEMPOTENCY_CONFLICT` (mapped in C#), no new row; `NewClaim` -> continue to step 3;
3. B3-OWNED session-row lock: `SELECT ... FOR UPDATE` on `verification_sessions` for `RequestedVerificationSessionId` via the new runtime-granted SD lock fn (2.9). If the row is ABSENT -> write immutable `Denied SESSION_NOT_FOUND` (resolved NULL, snapshot NULL, no B1/B2/policy read, no permit, zero AuthorizedRawClasses, expiry NULL) and COMMIT; remaining steps SKIPPED;
4. bind owner (`ClientApplicationId`), `SubjectRef`, `State` from the locked row; set `ResolvedVerificationSessionId = RequestedVerificationSessionId`;
5. require STRICT same-owner `owner == Actor.ClientApplicationId` (else `SESSION_NOT_OWNED`) AND `State == Completed` (else `SESSION_NOT_COMPLETED`);
6. **bounds gate (operational, NOT a business denial):** read `RawExportPermitTtlBoundsState`. If `!IsValid` -> ROLL BACK the whole transaction, surface the OPERATIONAL failure `PROD_RAW_EXPORT_PERMIT_TTL_BOUNDS_INVALID` (readiness/deployment), NO durable decision, NO idempotency claim;
7. **B1 is the eligibility authority:** `ResolveExportEligibilityForAuthorizationAsync(Actor.PrincipalId, PolicyId, PolicyVersion)` (holds 88B1 shared locks in this txn). If `State != Active` -> persist immutable `Denied EXPORT_ELIGIBILITY_INACTIVE` carrying B1 `PrimaryCause` + full `Causes[]` (this already covers catalog-approval, grant, lifecycle, rule-set, fulfillment) and COMMIT; remaining steps SKIPPED;
8. **(Active)** read the EXACT immutable 88A version `GetVersionAsync(PolicyId, PolicyVersion)` for `AllowedClasses` + `PermitTtlSeconds`. Treat CatalogApproved + present RECORD as an INVARIANT implied by B1 Active: if the exact record is absent or non-approved -> **INVARIANT FAILURE**: ROLL BACK, NO durable decision, NO idempotency claim (this is a should-never-happen consistency break between B1's read and the version read, not a business denial);
9. **policy TTL business gate:** with bounds VALID (step 6), require `PermitTtlSeconds` non-null AND `RawExportPermitTtlBoundsState.Allows(PermitTtlSeconds)` -> else persist `Denied POLICY_PERMIT_TTL_INVALID` and COMMIT; remaining steps SKIPPED. This is the E2 legacy disposition: an approved pre-E2 NULL-TTL row remains readable but is rejected at authorization; an approved version whose stored TTL is outside the CURRENT bounds is also rejected;
10. derive `EffectiveRequestedRawClasses` (Option-B, 2.8);
11. policy ceiling `EffectiveRequestedRawClasses subset-of AllowedClasses` else `Denied REQUESTED_RAW_CLASSES_NOT_ALLOWED`;
12. `ResolveSubjectExportConsentForAuthorizationAsync(ResolvedVerificationSessionId, PolicyId, PolicyVersion)` (holds 88B2 consent-scope shared lock in this txn); **snapshot-integrity assertions (2.6);** require `Effective` else `Denied SUBJECT_CONSENT_NOT_EFFECTIVE` carrying the B2 factual cause;
13. consent coverage `EffectiveRequestedRawClasses subset-of ConsentedRawClasses` else `Denied SUBJECT_CONSENT_CLASS_COVERAGE_INSUFFICIENT`;
14. write immutable decision + typed evidence (2.5) with `Outcome=Authorized`; write the permit (2.6b);
15. commit.

All held to commit: the B3 session-row lock + the 88B1 shared locks + the 88B2 consent-scope lock. Two-connection tests: authorize racing 88B1 grant-revoke / lifecycle / fulfillment-mutation, consent-withdraw, session-transition, duplicate-authorize -> never a stale `Authorized`; concurrent duplicate -> exactly one decision. (No runtime rule-set publisher; rule-publish race is not a B3 obligation.)

### 2.4 Idempotency + replay [dedicated principal-scoped table, greenfield]
`raw_export_authorization_idempotency` keyed `(PrincipalId, ClientApplicationId, RequestedVerificationSessionId, IdempotencyKey)`; the existing `append_idempotency_records` is session-scoped and unusable. Written/read via a SD claim/read fn. Semantic FINGERPRINT (2.7 codec) over exactly: `PrincipalId`, `ClientApplicationId`, `RequestedVerificationSessionId`, `PolicyId`, `PolicyVersion`, `PurposeCode`(server constant `SubjectRawBiometricExport`), the DERIVED `RawClassSelectionMode` (2.8), and (ExplicitSubset) canonical `RequestedRawClasses`. EXCLUDES `SubjectRef` (server-derived, evidence-bound), `ApiKeyId` (credential evidence only), `RecipientClientApplicationId` (derived, invariant-equal to ClientApplicationId).

**Idempotency claim/read state machine + timing.** The idempotency KEY TUPLE + FINGERPRINT is the idempotency authority - NOT any derived id. C# generates a FRESH UUIDv4 `ExportDecisionId` for a prospective new claim (no deterministic derivation). The SD fn `raw_export_claim_or_read_authorization_idempotency(...)` returns a TYPED result:
- `NewClaim` - the tuple was free; the fn inserted the idempotency row with the caller's fresh `ExportDecisionId` + `FingerprintHash`. B3 proceeds to evaluate + persist the decision under that id.
- `ExistingMatch` - the tuple exists with a MATCHING fingerprint. B3 does NOT re-evaluate session/B1/B2/policy and does NOT call the persist fn again; it LOADS and returns the existing immutable decision (+ permit/evidence) by the stored `ExportDecisionId`.
- `FingerprintConflict` - the tuple exists with a DIFFERENT fingerprint. The fn returns `outcome='FingerprintConflict'` with `export_decision_id = NULL`. Stable code `RAW_EXPORT_AUTHORIZATION_IDEMPOTENCY_CONFLICT`; ROLL BACK; no new decision/evidence/permit; no second idempotency row. **C# MUST NOT load or expose the existing decision graph on a fingerprint conflict** (no id is returned to load it with).

Concurrency: two identical concurrent claims race on the idempotency PK; the loser WAITS on the unique-key winner. Winner COMMITS -> loser re-reads and receives `ExistingMatch`. Winner ROLLS BACK -> loser may proceed as `NewClaim`. No committed idempotency row may ever reference a missing decision.

FK timing (pinned): the idempotency -> decision FK is `DEFERRABLE INITIALLY DEFERRED` (validated at COMMIT), so the claim + the decision are written in the SAME transaction; a `NewClaim` that rolls back leaves no orphan. Migration + a test prove that every committed idempotency row has its decision. Replay: same key+fingerprint => the SAME immutable decision (Authorized or Denied); same key+different fingerprint => `FingerprintConflict`; concurrent duplicates => exactly ONE decision; re-eval after `Denied` needs a NEW key; `DefaultPolicySet` vs `ExplicitSubset` under one key => `FingerprintConflict`.
